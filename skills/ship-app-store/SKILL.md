# Ship App Store

Use the repository's `shiplayer` CLI for all deterministic work. Do not recreate release logic in prose. Run `command -v shiplayer` first — the ShipLayer checkout's `npm run install-skill` links it onto PATH via `npm link`. If it does not resolve, fall back to that checkout's `./dist/index.js`; this private v0.1 package is not published to npm.

## Environment notes (check these before step 6)

- **No macOS/Xcode simulator on this machine.** Never attempt a local `xcodebuild`/simulator run for screenshots. Emit the harness template and `screenshots/capture-workflow.yml`, then hand off to a human or a macOS/Xcode CI runner — see [references/screenshots.md](references/screenshots.md).
- **Playwright on this machine needs a system browser.** This host's macOS (12.7.6) is below Playwright's bundled-Chromium floor, so `npm run export` fails to launch a browser unless you set `SHIPLAYER_PW_CHANNEL=chrome` (or another installed channel) first. Set it up front rather than waiting for the failure message.

## Workflow

1. Run `shiplayer analyze <repo> --json`. Treat heuristic findings as proposals, never as privacy/legal truth.
2. Run `shiplayer init <repo>` only when no manifest exists. Do not overwrite a manifest without an explicit user request.
3. Ask for confirmation only for facts the scanner cannot prove: pricing, availability, privacy collection/third parties, legal/trader status, App Review contact, and paywall behavior. Never infer that Zero Data Retention, no-training, or disabled provider collection means user data was not shared with the processors that received it. **Phrase every question as an observable fact about the running app — what the user taps, what appears next, what a screenshot shows — never as a schema field name.** If the user says they don't understand, or answers in a way that sounds unsure or guessed, do not record it as `confirmed`; re-ask in plainer terms until they describe something they actually observed. An arbitrary answer recorded as confirmed is worse than an unanswered question — see [references/questions.md](references/questions.md) for verbatim-usable templates covering the fields most often asked about (permission flows, monetization, AI sharing, third-party endpoints, privacy/legal/trader/agreements confirmations, App Review contact, data-processing tracking answers, export compliance/signing, availability) — apply the same observable-fact shape to any other blocking field it doesn't cover.
4. Draft `metadata.localizations.<locale>` (App Store name/subtitle/description/keywords/promotionalText/whatsNew) yourself from the app's real source and screenshots — see "App Store copy" below for the drafting rules and the checks that validate it. Present the draft to the user for approval; never set its `confirmation` to `confirmed` yourself.
5. Update and validate `shiplayer.yml`, then run `shiplayer prepare <repo>` and `shiplayer check <repo>`.
6. Get real screenshots before compositing marketing slides: run `shiplayer capture <repo>` to check for an existing UI-test harness, generate one via `prepare` if none exists, hand the resulting `screenshots/capture-workflow.yml` off to a human/macOS-CI runner (never run it yourself — see "Environment notes" above), then ingest the exported PNGs with `shiplayer capture <repo> --from <dir> --family <iphone|ipad> --locale <locale>`. Full contract in [references/screenshots.md](references/screenshots.md).
7. Draft each scenario's `screenshots.scenarios[].caption` in `shiplayer.yml`, then render `prepare`'s marketing composition project (`npm install && npm run export` in `shiplayer-release/screenshots/marketing/`, remembering `SHIPLAYER_PW_CHANNEL` from "Environment notes"), and re-run `shiplayer check <repo>`. Caption rules and the render pipeline are in [references/screenshots.md](references/screenshots.md).
8. Preview every generated screenshot, metadata field, privacy/support page, review note, and preflight warning with the user.
9. Run `shiplayer plan <repo>` first. Use `--remote` only with the user's credentials configured as environment variables; it is read-only.
10. Treat `apply` and `submit` as separate explicit user-authorized gates. Do not pass their confirmation flags on the user's behalf. In v0.1 explicit execution reports a manual/unsupported handoff and exits 3; explain that no operation happened.

## App Review hard gates

- `monetization` and `aiDataSharing` are cross-checked against the scan, not trusted at face value.
  - **Monetization.** The check runs for `free` **and** `paid-app` alike (neither models an in-app purchase). If `analyze`/`check` shows StoreKit purchase evidence (a `.purchase(` call corroborated by a StoreKit import or `.displayPrice` in the same file, `.displayPrice`/`ProductView` alone, a `.storekit` product ID, or a legacy `SKPaymentQueue`/`SKPaymentTransactionObserver` signal) while `monetization.type` is `free` or `paid-app`, `check` blocks loudly with `monetization.source-contradiction` (and `purchase.presentation`, since it cannot be verified for an undeclared model). A `free` declaration also needs its own `confirmation: confirmed` — an unconfirmed free declaration blocks on its own, evidence or not.
  - **AI data sharing.** Known providers split into two shapes. An **API-only host/subdomain** (`api.openai.com`, `api.anthropic.com`, `generativelanguage.googleapis.com`, a customer's `*.openai.azure.com`, and similar — nothing but the API is ever served there) is strong evidence regardless of path, covering real API paths beyond `/chat/completions`, e.g. `/v1/responses`, `/v1/images/generations`, `:generateContent`. A **mixed apex host**, where a provider's marketing/docs/legal/model-card pages and its API plausibly share the same bare hostname (`openai.com`, `anthropic.com`, `huggingface.co`, `openrouter.ai`, `x.ai`, and similar), is the inverse: only an inference-API-shaped path is strong evidence there — a provider's real privacy-policy page, a model card, a blog post, or a bare root path only **warns** (`ai-sharing.possible-processor-link`) for the AI-contradiction gate specifically, and no override is needed to clear that warning. **That warning is not the whole story for the endpoint**, though: every scanner finding, including a plain policy link, separately needs a confirmed `externalServiceDecisions` disposition (`source.external.<findingId>`) or `check` blocks on that regardless — see [references/ai-data-sharing.md](references/ai-data-sharing.md). Separately, an **unrecognized** host whose path is still inference-API-shaped also blocks the AI-contradiction gate, but under a distinct id, `ai-sharing.source-contradiction-ambiguous-endpoint` (the proxied-endpoint case: an app's own backend forwarding to an AI provider) — treat this exactly like the named-provider case when helping the user, but do not claim ShipLayer identified a specific provider when it only matched a path shape; this is a deliberate trade-off, not a fully solved classification, so route it to a human override rather than treating either outcome as certain. `init` only ever proposes `kind: "ai"` for an endpoint that actually classified as a known provider — a correctly-classified `kind: "ai"` proposal by itself requires an AI disclosure even before `aiPipelineRecipient` is set, so do not "fix" a false block by silently changing `kind` away from `"ai"` on a real provider; only change it if the user confirms the endpoint genuinely isn't one.
  - **Known gap:** these checks only see literal URLs actually present in the repository (source code, Info.plist string values, `.xcconfig`/`.pbxproj`/`project.yml` build settings, including arbitrary user-defined URL-valued settings). A base URL injected only via a build/CI environment variable or secret, with a `$(VARIABLE)` indirection and no literal value anywhere in the tracked repo, will not be detected. If you know (from the user, from a Cloudflare Worker or backend in the same repo, from CI config) that the app proxies to a third-party AI provider even though ShipLayer found no direct endpoint, say so and help the user declare `aiDataSharing` anyway — do not treat a clean scan as proof there is no AI data sharing.
  - Never resolve a contradiction blocker by leaving the manifest blank or guessing at the missing fields — either help the user declare the real IAP/subscription model or AI data-sharing disclosure, or, only when the user confirms the finding is not real (e.g. dead code, a docs-only link, sandbox-only scaffolding), add a `sourceContradictionOverrides` entry naming the exact blocker id with a human-authored `reason`, real `evidence` paths, and `confirmation: confirmed`. `sourceContradictionOverrides` currently covers exactly four blockers: `monetization.source-contradiction`, `ai-sharing.source-contradiction:<findingKey>` (including the ambiguous-endpoint variant below), `purchase.unavailable-source` (see the purchase-presentation gate below), and `source.insecure-endpoint.<findingId>` (see the insecure-endpoint bullet below) — no other blocker id can be overridden this way. The evidence path(s) must actually exist and must cite the same file(s) the flagged finding itself points to — citing an unrelated file (e.g. `NOTES.md`) does not and must not resolve the block; ShipLayer verifies the overlap itself, but never construct or suggest an override that doesn't genuinely address the flagged evidence. Never fabricate that reason yourself or set `confirmation: confirmed` without the user's explicit say-so — an override is a human decision, not a heuristic one.
  - **A heuristic can be wrong, and that is a legitimate outcome, not a dead end.** Every gate in this section is a pattern match over source, not proof of runtime behavior — it can fail to recognize a real app that satisfies Apple's actual requirement through a shape the pattern doesn't cover (a custom button/state-machine component, an extra layer of indirection between a view and the code that calls `.purchase(`, and similar). When you have read the real code and confirmed by hand that it already does the right thing, the correct response is a `sourceContradictionOverrides` entry explaining what the heuristic missed and why the app is actually compliant — **never** add code whose only purpose is to be recognized by the scanner (a literal, otherwise-unused `Button`/`.purchase(` call, a hard-coded property added only to match a pattern, dead branches nothing ever renders). Code written solely to satisfy a heuristic is worse than an unresolved blocker: it ships something no user path exercises while looking, to the next reader, like the real purchase flow. An override downgrades the finding to a visible warning — it is auditable and reversible — it never silently clears it, and Apple review sees the real code either way.
- **Permission-flow (5.1.1(iv)).** For every runtime permission-request call `analyze`/`check` detects (camera, microphone, photo-library, location, notifications, contacts, calendar, reminders, media-library, speech-recognition, motion, tracking; Swift-syntax only in v0.1 — an Objective-C-only request is not detected), `shiplayer.yml` needs a `permissionFlows` entry recording two runtime facts no scanner can prove: whether a dismissible custom screen can appear before the system permission prompt, and whether the denied-access path offers a link to Settings. **Never guess either value or set `confirmation` to `confirmed` yourself, even if the code looks fine to you — ask the user, phrased around what they actually see on screen, not the field names.** [references/questions.md](references/questions.md) has the verbatim template that worked in the field: describe the real trigger, ask what appears immediately after, and give the "if you see X that's compliant, if you see Y that's the violation" framing. `init` only ever proposes `needs-human-confirmation`.

  **A confirmed answer is not automatically a passing answer.** `permission-flow.<category>.dismissible-screen` blocks the moment the user confirms `dismissibleScreenBeforePrompt: true` — that is a written admission of the 5.1.1(iv) violation, not a resolved question, and it blocks even when nothing else detects a problem. Likewise `permission-flow.<category>.denied-path-settings-link` blocks unless the user confirms `deniedPathOffersSettingsLink: true`. Don't treat either "yes" as done — help fix the actual flow (restructure so the request is reachable directly, or the custom screen always proceeds with no Cancel/dismiss; add a denied-state Settings link) and re-confirm only once the real behavior changed. `permission-flow.<category>.settings-link-heuristic` is informational only (warn/pass, never block) — it corroborates the declaration but never overrides it either way. If `permission-flow.<category>.sheet-gated` blocks, ShipLayer's own heuristic found the request reachable only from inside a dismissible presentation (the BackYet 5.1.1(iv) rejection shape: a "How would you like to add it?" sheet with a Cancel button in front of the camera prompt) — help restructure the flow, or, only if the user confirms after checking the real on-device behavior that the screen truly cannot be dismissed, set `dismissibleScreenBeforePrompt: false` and `confirmation: confirmed`.
- For any third-party AI feature, require `aiDataSharing.enabled: true`, exact data sent, purpose, and every intermediary/provider recipient. Mark every processor in that feature pipeline `aiPipelineRecipient: true` while keeping unrelated analytics/payments `false`. Production consent source—not test/fixture/docs text—must render the declared affirmative action, non-AI decline path, and Privacy Policy link before transmission. `dataSent`, `purpose`, and `processorNames` are matched as **literal case-insensitive substrings** of both the consent source and the privacy-policy text, not judged semantically — draft them as the app's actual on-screen/policy wording from the start. The affirmative action must explicitly say data is sent/shared/uploaded/transmitted; `check` — not manifest validation — is what judges this (`ai-sharing.consent-action-language`), so a manifest with the app's real button label always loads even when that label still needs rewording. `externalProcessors[].purpose` is Apple's fixed six-value App Privacy purpose enum, not free text; descriptive detail belongs in `dataCategories` and the policy prose instead. Full matching/enum detail and the field-confusion trap (`aiDataSharing.purpose` is free text; `externalProcessors[].purpose` is not) are in [references/ai-data-sharing.md](references/ai-data-sharing.md).
- **Every confirmed `externalProcessors[]` row needs its own `collectionDetermination`, and confirming a processor is not the end of the question** — the App Privacy questionnaire (`dataProcessing[]`) is a separate, connected manifest section, not an independent one: for each of that processor's `dataCategories`, `check` (`privacy.processor.<name>.<category>`) demands a matching confirmed `dataProcessing` row unless `collectionDetermination` says otherwise. `collectionDetermination` answers one narrow legal question — is this processor's *receipt* of data "collection" under Apple's own definition ("transmitting data off the device in a way that allows you and/or your third-party partners to access it for a period longer than what is necessary to service the transmitted request in real time" — developer.apple.com/app-store/app-privacy-details/)? Data sent only to service a request in real time and not retained beyond that (Apple's own examples: an auth token or IP address on a server call, or data discarded immediately after servicing the request) falls outside that definition entirely and needs no `dataProcessing` row at all — this is the common shape for CDN edge traffic and read-only API calls, not the same thing as ZDR/no-training. It is `needs-human-confirmation` by default (absent is treated identically) and blocks (`privacy.processor.<name>.collection-determination`) until a human answers `collection` or `not-collection`; `not-collection` additionally requires `notCollectionAttestation` with literal `dataNotRetainedBeyondRealTimeService: true` and literal human confirmation. v0.1 has one automatic evidence shape: `vendor-documentation` with `evidence.kind: processor-privacy-policy` and the exact credential-free canonical `privacyPolicyUrl` on the processor's exact host. The policy route must itself be privacy/data-protection/data-collection/retention/DPA shaped; no parent-domain, registrable-domain, shared-host tenant, generic ZDR, or marketing-page inference is allowed. Repository/source paths cannot establish runtime reachability or retention, so legacy `first-party-implementation`/`repo-path` evidence always blocks with migration guidance; confidential `contract-dpa`/`written-vendor-confirmation` material also remains fail-closed. ShipLayer verifies only policy-host/path linkage and relevant endpoint dispositions — **never** document content, code semantics, or retention truth. An exact runtime/API endpoint linked to a processor cannot also be declared `not-an-external-processor`; a separate docs/privacy link on that host may be. Arbitrary public URLs and generic ZDR/no-training links cannot clear the gate; do not put credentials, credential-shaped URL paths, query strings, or fragments in structured attestation evidence (ordinary support and privacy URLs may use benign paths, queries, and fragments). **Never set `collection` to clear the per-category blockers when you are not sure it is true, and never set `not-collection` to make them disappear** — either can be the honest answer, but only the human who actually knows what the processor does with the data can say which. A free-text `collectionDeterminationReason` is audit-only: ShipLayer deliberately does not parse it as proof in any language. See [references/questions.md](references/questions.md) for the observable-fact question to ask.
- **`source.insecure-endpoint`** fires on a real, live `http://` reference in scanned source/config — never on one that exists only inside a `//`/`/* */` comment, and never on a loopback (`127.0.0.1`, `::1`, `localhost`) or RFC1918/link-local private address, since neither is a transport-security risk App Transport Security governs. A real `http://` reference to a public host still blocks, and is resolvable through the same `sourceContradictionOverrides` mechanism as the blockers above when a human confirms the finding is not a real risk (e.g. sandboxed test infrastructure) — never by deleting a legitimate comment or code path just to stop the scanner from seeing it.
- Require a matching public `.md`, `.markdown`, `.html`, `.htm`, or `.txt` privacy-policy artifact that explains how data is obtained/transmitted, every use and recipient, retention/deletion, and same-or-equal processor protection. Do not treat terms-only disclosure, unused code constants, or manifest booleans as sufficient.
- For every non-consumable or subscription, require production evidence that StoreKit `Product.displayPrice` reaches visible iOS release UI and that a custom purchase Button is structurally withheld in the available-product branch or uses a direct safe disabled predicate while product/price is unavailable (`purchase.unavailable-source`). Rendered `ProductView`/`SubscriptionStoreView`, and rendered `StoreView` for non-consumables, may own the purchase action when they use verified built-in styles. Known iOS, StoreKit, and SwiftUI compilation guards are eligible; arbitrary module guards are not. Require direct, non-compound assertions inside credible XCTest or Swift Testing methods for both visible pricing and the unavailable state. Never approve hard-coded, debug-only, simulator-only, other-platform-only, unknown-conditional, or unused prices/views.
  - `purchase.unavailable-source` recognizes three shapes. First, a rendered built-in-style `ProductView`/`SubscriptionStoreView`/`StoreView` — StoreKit owns the unavailable state, so the check short-circuits and never fires at all. Otherwise it needs either a purchase `Button` nested inside an `if let` guard whose bound name contains `product` or `price` (`if let loadedProduct` matches; the name need not be exactly `product`), or a `Button` whose own body contains `.purchase(` gated by a direct safe `.disabled(...)` predicate (loading/nil/available-style checks — never a compound `&&`/`||` expression). A real paywall that gates purchase through a custom button component, a bound enum case, or a closure handed down to a different type — proven safe by reading the actual control flow, not by the file merely compiling — can still false-block here. Verify the real behavior yourself before concluding it's a false block, then add a `purchase.unavailable-source` override (evidence citing the same `purchasePresentation.sourceEvidence` file(s) the block names) rather than restructuring a working paywall, or inserting an unused `Button`/`.purchase(` call, just to satisfy the pattern.
- For subscriptions, also require production and assertion-backed test evidence that the billing period, applicable offer terms, and Terms/Privacy links are visible before purchase. `SubscriptionStoreView` with a built-in `SubscriptionStoreControlStyle` may own the automatic production presentation; an unverified custom control style cannot. Tests and human confirmation must still verify those disclosures.

## App Store copy

- `metadata.localizations.<locale>` (`name`, `subtitle`, `description`, `keywords`, `promotionalText`, `whatsNew`) is a human-reviewable proposal you draft, never a fact ShipLayer invents — `init` always leaves it absent and records an unresolved question naming exactly what to write. Read the app's real source (views, feature flags, the actual StoreKit products) and its actual screenshots before drafting; describe only what the app does today, not a roadmap, an aspiration, or a feature you assume exists.
- Write for the store, not for engineers. `subtitle` (max 30 characters) sells one idea, not a feature list. The first one to two lines of `description` are what a user sees before tapping "more" on the product page — put the strongest, most concrete value statement there, not a company history or a bullet-list preamble.
- Never state a specific price (`$`, `€`, `£`, a numeric "USD"/"dollars" amount) — App Review 2.3.12 rejects this since price varies by storefront and StoreKit already shows it live. Never reference another platform or storefront ("Android", "Google Play", "Windows", "web version" — 2.3.10). Never leave placeholder text ("Lorem ipsum", "TODO", "XXX", "<your app>"). `check` **blocks** on all three categories (`metadata.<locale>.<field>.placeholder` / `.other-platform`); it only **warns** on a specific price, beta/trial/test language, and unsubstantiated superlatives ("#1", "best app") since those are judgment calls — treat a warning as something to fix before submission, not something to ignore because it did not block.
- Every field you draft goes in with `confirmation` left unset (the schema/generator treat an absent value as `needs-human-confirmation`, exactly like a screenshot scenario's confirmation). **Never set `metadata.localizations.<locale>.confirmation: confirmed` yourself** — present the drafted copy to the user for their own review and approval, exactly like every other proposal in this manifest (monetization, permission flows, AI disclosures). `shiplayer check` blocks on anything other than a literal `confirmed`, and an absent value is never read as approved.
- Copy is cross-checked against what the manifest actually declares the app does, not trusted at face value, and the checks are *type-aware*: a zero-cost claim ("completely free", "free app", "free to download/use", ...) blocks whenever `monetization.type` is not `free` — including `paid-app`, since paying once for the app is still not free. A "no in-app purchases"/"no IAP"/"no purchase necessary" claim only blocks when the declared type actually models an in-app purchase (`non-consumables`/`subscriptions`) — it is a *true* statement for `paid-app` (the purchase is the app itself, not an in-app one) and never blocks there. "No hidden fees/costs" is not treated as a purchase claim at all — that phrase is a transparency statement, honestly sayable regardless of monetization type. "Free to try" is exempted only when a subscription product actually declares a `free-trial` `introductoryOffer`; without one, it still blocks (Apple requires trial terms be disclosed, but only when a trial genuinely exists). A "no subscription"/"one-time purchase" claim, or the inverse — claiming a purchase/subscription on a genuinely free app — also **blocks** with `metadata.<locale>.<field>.monetization-contradiction`. Claiming iPad support while `app.deviceFamilies` excludes `ipad` **blocks** with `.device-family-contradiction`; the negation check is scoped to the SAME CLAUSE as the claim (it stops at the nearest sentence-ending punctuation or comma), not a fixed character window — so an unrelated negation elsewhere in the sentence (e.g. "There are no ads at all, and it looks stunning on iPad.") cannot silently clear a genuine claim, while a same-clause negation (e.g. "not available on iPad" or "iPhone only") still does. If `aiDataSharing.enabled` is true but no locale's copy mentions AI or names a declared AI processor, `check` **warns** (`metadata.ai-mention`) — this app has previously been rejected for undisclosed AI processing, so disclose the AI feature in the listing itself, not only in the App Privacy questionnaire.
- These contradiction checks are pattern-based over natural language, not proof, and are deliberately conservative: they never match a bare "free" (so "hassle-free", "ad-free", and "distraction-free app" never false-block), and the "Windows" platform check is case-sensitive (so the common lowercase word — "manage multiple windows" — never false-blocks). Every guard scans *every* match in a field, not only the first, so an early guarded/negated match (e.g. "ad-free" hyphen-compounded, or a "no in-app purchase" negation) can never hide a genuine, unguarded claim appearing later in the same text. Do not treat a clean pass as a guarantee the copy is accurate, and never "fix" a block by rewording around the pattern instead of checking whether the copy is actually true — if `check` blocks and the copy is honest, that is a false positive to report, not a prompt to obscure the same claim in different words.
- Keyword hygiene: `keywords` has a 100-character budget counted as the comma-joined string App Store Connect actually accepts, not the array's item count. `check` **warns** (never blocks) on leading/trailing whitespace inside a keyword (wastes budget once joined with commas), on a keyword that repeats a word already in `name`/`subtitle` (Apple indexes those separately, so repeating wastes budget), and on likely plural/singular duplicates of the same word within the keyword list. Resolve these before submission even though they will not stop `prepare`/`check` from otherwise succeeding.

## Safety

- Never put credentials, `.p8` contents, login passwords, banking data, or tax details in `shiplayer.yml` or generated artifacts.
- Never make or imply legal/privacy compliance. Require explicit human confirmation.
- Do not create initial app records, accept agreements, alter tax/banking/trader declarations, or submit an app without direct user approval.
- Use `shiplayer capture` to inspect the deterministic harness hand-off. v0.1 does not execute generic Simulator capture commands; only run a repository-owned, reviewed UI-test harness on macOS/Xcode — never attempt one yourself on a machine without it (see "Environment notes" above).
