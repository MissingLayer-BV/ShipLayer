# Automation boundaries

ShipLayer can prepare facts, drafts, asset plans, and an idempotent remote change plan. It cannot create legal truth from source code.

| Capability | v0.1 boundary |
|---|---|
| Swift/Xcode facts | Detect with evidence; report contradictions and unknowns. |
| Monetization vs. source | `check`/`prepare` cross-check every declaration with no in-app-purchase capability (`free` **and** `paid-app`) against scanned StoreKit purchase evidence (a corroborated `Product.purchase()`, `.displayPrice`/`ProductView`, `.storekit` product IDs, or a legacy `SKPaymentQueue`/`SKPaymentTransactionObserver` signal). A disagreement is a loud `monetization.source-contradiction` block, resolvable only by fixing the declaration or recording a confirmed `sourceContradictionOverrides` entry whose evidence intersects the flagged finding — never by silence, and never by simply picking a different non-IAP monetization type. `free` additionally requires its own human `confirmation`. |
| AI data sharing vs. source | `check`/`prepare` cross-check `aiDataSharing.enabled` against scanned endpoints. An API-only host/subdomain (`api.openai.com`, `api.anthropic.com`, `generativelanguage.googleapis.com`, a customer's `*.openai.azure.com`, and similar — no marketing page ever lives there) is strong evidence regardless of path. A mixed apex host, where marketing/docs/legal/model-card pages and the API plausibly share one hostname (`openai.com`, `anthropic.com`, `huggingface.co`, `openrouter.ai`, and similar), is strong evidence only when the path is itself inference-API-shaped (`/chat/completions`, `/v1/messages`, `/generate`, `/inference`, `/completions`, `/embeddings`); every other path there — including a provider's real privacy-policy/legal/model-card/blog page — only warns. An unrecognized host whose path is still inference-API-shaped blocks too, under the distinct `ai-sharing.source-contradiction-ambiguous-endpoint` id (the proxied-endpoint case) — a deliberate trade-off (catching same-shaped proxies necessarily also catches an unrelated `/v1/messages`-shaped API), left to a human override rather than resolved automatically. `init` only proposes `kind: "ai"` (which alone forces the separate `ai-sharing.declaration` check) for an endpoint that actually classified as a known provider; a policy link or an ambiguous unrecognized-host endpoint is proposed as `kind: "network"` so it stays resolvable purely through `sourceContradictionOverrides`. Resolvable only by declaring `aiDataSharing` or recording a confirmed `sourceContradictionOverrides` entry naming that exact endpoint finding with intersecting, existing evidence. **Known gap:** a base URL only ever injected via a build/CI environment variable, with no literal value anywhere in the tracked repository, cannot be found by static scanning. |
| Privacy and legal copy | Draft from confirmed facts; human reviews and publishes. Generated drafts never assert "none/no confirmed X" when the scan found unresolved endpoint/SDK/StoreKit evidence — they name the unresolved finding instead. |
| App Store copy vs. manifest | ShipLayer never drafts `metadata.localizations.<locale>` (name/subtitle/description/keywords/promotionalText/whatsNew) itself — `init` always leaves it absent and records an unresolved question naming exactly what to draft; `check` blocks unless `metadata.localizations.<locale>.confirmation` is exactly `confirmed`, same as every other proposal. Robust, deterministic checks (block): per-field character limits, Apple's requirement that every keyword be longer than two characters, the 100-UTF-8-byte comma-joined keyword budget, placeholder text left in ("Lorem ipsum", "TODO", "XXX", "<your app>"), and an other-platform reference (2.3.10: "Android", "Google Play", "Windows", "Web version"). Heuristic cross-checks against the manifest (block, deliberately narrow to avoid false positives): a zero-cost claim ("completely free", "free app", ...) blocks unless `monetization.type` is `free`, including for `paid-app` (a paid download is not free); a "no in-app purchases"/"no IAP" claim blocks only when the declared type actually models one (`non-consumables`/`subscriptions`) — it is *true*, and never blocks, for `paid-app`; "no hidden fees/costs" is not treated as a purchase claim at all (a transparency statement, not a no-purchase one); "free to try" is exempted only when a subscription product actually declares a `free-trial` `introductoryOffer`. Copy claiming iPad support while `app.deviceFamilies` excludes `ipad` blocks too — the negation check is scoped to the same clause (stops at the nearest sentence-ending punctuation or comma), not a fixed character window. Every guard scans all matches in a field, not only the first, so an early guarded/negated match cannot hide a later genuine claim (no bare "free" match; case-sensitive "Windows" only). Heuristic warnings (never block, judgment calls): a specific price, beta/trial/test language, unsubstantiated superlatives, keyword whitespace/name-overlap/plural-duplicate hygiene, and — since this app has previously been rejected for undisclosed AI processing — no locale's copy mentioning AI while `aiDataSharing.enabled` is true. |
| Permission-flow vs. source (5.1.1(iv)) | Detection is Swift-syntax-only in v0.1 (an Objective-C-only permission request is not detected and gets none of these gates, even though the scanner reads `.m`/`.mm`/`.h` for other checks). Design: declarations block, heuristics warn/corroborate, never the reverse. `permission-flow.<category>.confirmation` (always required): blocks unless `permissionFlows` has a `confirmed` entry for the category, answering both whether a dismissible custom screen can appear before the system prompt and whether the denied-access path offers a link to Settings. `permission-flow.<category>.dismissible-screen`: once confirmed, blocks on `dismissibleScreenBeforePrompt: true` by itself, a written admission of the violation, independent of any heuristic. `permission-flow.<category>.denied-path-settings-link`: once confirmed, blocks unless `deniedPathOffersSettingsLink: true`; this declaration, not a text heuristic, is authoritative. `permission-flow.<category>.settings-link-heuristic` (advisory, warn/pass, never block): corroborates the declaration via same-function/same-region correlation of a `.denied`/`.restricted` marker with `UIApplication.openSettingsURLString` (directly, or through a `@State` flag read by a separate presentation), plus a one-hop join through a type the request-site file declares, covering the ordinary SwiftUI MVVM split where a manager requests and a different view renders the denied Settings UI (BackYet's own real `notifications` architecture). Narrower than "a Settings link exists anywhere in the app", but the join is not category-scoped and the same-region span is capped, so a `pass` is a weak textual signal rather than proof; the declaration gates this check. `permission-flow.<category>.sheet-gated` (heuristic, clearable): blocks only when the request is reachable, in a given file, exclusively from inside a `.sheet`/`.confirmationDialog`/`.alert`/`.popover` presentation (including via that presentation's `onDismiss` callback), BackYet's real rejected shape, clearable only by a confirmed `permissionFlows` entry with `dismissibleScreenBeforePrompt: false`. `init` only ever proposes `needs-human-confirmation` entries and never guesses either boolean's true value; a confirmed "yes it's dismissible" or "no Settings link" answer blocks exactly as loudly as an unanswered one. |
| Screenshot capture | `init` detects an existing `keepScreenshot(named:)`-shaped XCUITest harness (see `isXCUITestSourcePath` in `src/evidence.ts`, deliberately separate from the production-evidence predicates) and proposes its scenarios as `screenshots.scenarios`, always `needs-human-confirmation` — never silently confirmed. `prepare` additionally emits a fillable harness template, its written contract, and a `workflow_dispatch`-only capture workflow into `shiplayer-release/screenshots/` (never into the target repository's own source tree or `.github/`; see "CI workflow generation" below). Each manual run chooses one declared family/locale configuration and appends that locale's safely encoded `screenshots.localizations.<locale>.launchArguments` to every scenario. `capture --from DIR --family F --locale L` genuinely, recursively ingests and validates already-exported PNGs into `screenshots.rawOutputDir`; ShipLayer still executes no generic `xcodebuild`/simulator command itself, and still never invents navigation or translates pixels. |
| CI workflow generation | `prepare` can write `screenshots/capture-workflow.yml` **as an artifact inside the generated `shiplayer-release/` package only** — never into the app repository's `.github/workflows/`, never committed, never dispatched. ShipLayer itself still adds no CI to itself and never triggers cloud CI. The generated workflow is `workflow_dispatch`-only (no `push`/`pull_request`/`schedule`), a single explicitly selected family/locale simulator with no matrix, a concurrency guard, an explicit job timeout, and a header comment stating macOS runners bill at roughly 10x and that this must never be made automatic. A human must manually copy it into the app repository and press "Run workflow" themselves. |
| Marketing screenshot composition | `prepare` emits a self-contained project at `shiplayer-release/screenshots/marketing/` whose generated `package.json` declares exactly one exactly-pinned dependency, Playwright — the ShipLayer CLI itself gains no browser dependency, runs no `npm install`, downloads no browser, and executes nothing. Every slide is a standalone HTML file referencing only local files by relative path (system font stack; no remote font/script/image reference), so rendering itself needs no network access. A human/agent runs the two documented commands (`npm install`, `npm run export`) to produce final PNGs; alternatively, a repository's already-authorized composite-action workflow may explicitly set `render-screenshots: "true"`, which installs that exact dependency without lifecycle scripts and renders with the runner's installed Chrome before its plan/apply command. `check` then validates whatever exists at `screenshots/final/` (same rules as raw captures — dimensions, uniform size, count, no alpha), staying silent rather than blocking when nothing has been rendered yet. |
| App Store Connect | JWT-based GET-only planning plus a separately gated write adapter for existing app records: version, localized product-page copy/URLs, categories, copyright/release mode, App Review details, selected build, and screenshot sets/assets/order. Every apply requires a blocker-free preflight, `sync.mode: apply`, and explicit CLI confirmation. Mutations are not automatically retried; failures report possible partial state and reruns reconcile current state. |
| Subscriptions/IAP | Block readiness unless comment-stripped, role-checked production source visibly presents StoreKit pricing (or a StoreKit-owned merchandising view), handles unavailable/loading state, and conventional test assertions verify both. Custom subscription source and every subscription test must cover period, offers, and legal links; `SubscriptionStoreView` may own their automatic source presentation. Human verifies StoreKit/App Store Connect and sandbox behavior. |
| Third-party AI | Block readiness without explicit AI-pipeline roles for every recipient/intermediary, role-checked production consent source proving exact data/recipient/purpose/actions/privacy link, and policy evidence for method/uses/retention/protection. Human confirms legal truth and processor protection. |
| Initial app record, agreements, tax/banking, trader | Human/App Store Connect UI only. |
| Apply / final submission | `plan --remote` and `apply` without flags are read-only. `apply --apply --yes-i-understand` writes only after the user has reviewed the plan and opted the manifest into `sync.mode: apply`. `submit` remains separate, human-controlled, and unsupported; explicit submit still exits 3 without submitting. |

Never add secret keys to a manifest, fixture, generated package, or terminal output. Never browser-scrape App Store Connect.
